# 岗位参考匹配度

## 数据来源

岗位列表与岗位详情的 `matchScore` 使用同一岗位级计算，不再复用 `t_tal.tal_matched_score`。后者是企业人才记录上的评分，未关联当前岗位，同一企业的多个岗位因此会出现相同分数。

当前参考分以真实简历和岗位字段进行规则计算，不调用 AI 模型，不使用随机数、固定基础分或浏览行为。相同条件得到相同分数是允许的，不刻意制造差异。

## 规则

- 首页推荐区先通过 `GET /agent/v1/resumes` 读取本人简历，默认选择有效默认简历（没有默认项时选择列表首项），也可手动切换；选择仅影响本次推荐，不修改默认简历。
- 推荐请求 `GET /agent/v1/jobs` 新增可选 `resumeId`，根据该简历的技能、方向计算分数并在数据库排序后分页。后端先校验该简历属于当前用户且有效，拒绝不存在、已删除及他人简历，不静默回退到默认简历。
- 未传 `resumeId` 的旧调用保持有效默认简历优先，无默认时取最近更新简历；不会合并多份简历的技能。
- 岗位技能覆盖占 60 分：该简历匹配到的岗位技能数 / 岗位技能总数。技能忽略大小写和两端空格并去重，使用名称精确匹配，不声称具备语义相似度能力。
- 求职方向占 25 分：显式选择时使用该简历的求职方向，缺失则取该简历的期望岗位，不借用其他简历或个人资料。未传简历的旧调用保持个人资料方向回退。与岗位标题做字面包含匹配。
- 城市偏好占 15 分：显式选择时使用该简历的期望城市，缺失取该简历的当前城市；旧调用仍用个人资料。与岗位城市比较。
- 缺失维度不加分；没有简历技能也没有求职方向时返回 `null`，界面提示完善资料，不伪造百分比。
- 分数保留一位小数，在数据库完成排序后再分页。列表与详情使用同一表达式。
- 分页总数使用 `selectJobList_COUNT` 和列表共享的筛选条件，避免分页插件解析复杂评分表达式导致请求长时间等待。

参考分不代表录用概率、企业评价或完整人岗能力评估，暂未包含学历、工作年限、薪资期望、浏览历史和模型语义分析。

切换简历会恢复匹配度排序；搜索、排序和刷新继续携带选中简历，较早的响应不能覆盖新推荐。无简历显示普通在招岗位并提供创建入口，读取失败显示重试，不伪装推荐成功。进入详情或投递页时传递推荐简历，投递确认页只从本人有效简历列表预选，仍需用户确认后才发送，不自动投递。

## 验证

`AgentJobMatchScoreTest` 使用真实 MyBatis 映射与隔离 H2 数据库验证同企业不同岗位、用户隔离、默认/最近简历、个人资料回退、缺失资料、重复技能、零技能岗位、小数精度、分页排序及筛选总数。

后端 SQL 修改必须重新构建并重启实际后端后才会生效；只刷新前端不会替换运行中 JAR 内的 Mapper。本改动没有数据库迁移，不修改已有企业人才评分。
