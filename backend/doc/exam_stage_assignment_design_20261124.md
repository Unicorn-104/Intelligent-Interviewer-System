# 笔试阶段化与面试预约设计

## 目标

岗位流程中的在线笔试使用岗位级考试场次，面试继续使用候选人级预约。笔试场次、候选人资格、答题记录和流程结果分别保存，避免把笔试当作面试预约。

## 数据边界

- 流程模板：发布流程时生成新的不可变模板版本，旧模板和阶段定义保留；岗位只绑定最新版本。
- 投递流程实例：记录候选人投递时绑定的模板版本，旧投递不跟随岗位当前流程改变。
- 考试场次：绑定 `position_id + stage_id + template_version`，保存试卷、时间窗、阈值和次数规则。
- 场次分配：`t_exam_schedule_candidate` 保存投递、流程实例、阶段、通知和撤销审计；同一场次和候选人唯一，撤销后复用原行并递增修订号。
- 考试记录：`t_exam_record` 只代表一次答题尝试，设备检测状态 0 不算开始。
- 流程节点：笔试节点按 `process_instance_id + stage_id` 代表逻辑阶段，考试记录按尝试聚合；任一次有效尝试通过后阶段结果保持通过。

## 业务规则

1. 候选人只能访问有效分配关系对应的考试场次，不能仅凭岗位投递访问。
2. 通知默认只发送给有效分配候选人；至少一个渠道成功才更新 `notify_at`，全失败允许重试。
3. 场次截止前可以追加候选人，但剩余时间必须不少于试卷时长；截止后不能再加入候选人。
4. 首次真实开考后冻结试卷、阈值、最大次数和时间核心规则。
5. 面试接口拒绝 `stage_type=1`；面试前置校验必须按阶段 ID 和顺序验证所有必选笔试阶段已通过。
6. 已通过阶段禁止再次创建有效分配；分配撤销和重新加入必须保留历史记录。

## 接口与页面

- `POST /enterprise/exam/schedules/{id}/candidates`：幂等加入候选人。
- `GET/POST /enterprise/exam/schedules`：场次列表和创建，创建时必须传 `stageId`。
- `GET /enterprise/exam/schedules/{id}/notify-targets` 与通知接口只读取有效分配。
- 候选人端考试入口和考试列表只读取有效分配。
- E-App 顶部入口显示“笔试安排”；独立页面可新建场次或复用进行中场次。
- 邀请面试页保留笔试阶段卡片，但改为只读提示，不展示面试时间和面试官设置。

## 迁移顺序

1. 备份岗位、流程模板、投递实例、考试场次、考试记录和流程节点。
2. 执行 `migration_exam_stage_assignment_20261124.sql`。
3. 回填旧投递模板版本、旧场次阶段和可确认的候选人分配；无法确认的记录标记 `legacy`，不自动扩大访问权限。
4. 通过 `record_id -> exam_schedule -> stage` 回填旧笔试节点；无法确认阶段的节点不参与阶段聚合。
5. 完成回填核对后，再考虑将新场次的阶段字段收紧为非空及增加阶段级唯一约束。
6. 部署后端后再安装 E-App，验证未分配访问、批量加入、追加、笔试通过后面试解锁和历史数据展示。

回滚时先停止新版本应用并恢复代码，再按 `rollback_exam_stage_assignment_20261124.sql` 回滚新增结构；已产生的考试记录和流程结果需要人工核对，不能直接删除。
