> 适用范围：E-App 企业投递简历独立存储（企业简历快照）首次生产迁移
> 生产库：`recruit_agent`，当前阶段 `STAGE0_ORIGINAL`
> 本清单基于对仓库 SQL、Java 源码、隔离演练报告与生产只读核查结果的静态核对，**不代表已在生产执行**。
> 结论口径：`PASS`（通过）/ `WARNING`（需关注，不阻断）/ `BLOCKED`（阻断，必须先处理）/ `NOT_VERIFIED`（尚未实际执行验证）

## 二、P0 数据覆盖核对（逐项回答）

### 1. 10 条历史投递能否完整迁移？—— **PASS**

- `03_backfill.sql` 步骤 1（第 28–50 行）为每条尚无快照的投递插入主表，关联条件为
  `JOIN t_tal t ON t.tal_id = a.app_candidate_id`（第 46 行，候选人级别关联）。
- 生产 10 条投递的候选人均存在、简历引用正常 10/10，预期回填后快照主表 = **10 行**。
- 唯一静默遗漏风险是“候选人在 t_tal 不存在”的孤儿投递；脚本已在文末提供
  **异常检查 A**（第 325–330 行）。**用户执行 03 后必须确认该查询返回 0 行。**

### 2. 两条软删除简历是否会被遗漏？—— **PASS（不会遗漏）**

- 步骤 1 对 `t_res_base` 使用 `LEFT JOIN ... ON b.rbs_id = a.app_resume_id`（第 47 行），
  **关联条件不含 `rbs_status` 过滤**，软删除（`rbs_status=0`）简历主记录仍能匹配。
- 匹配成功即标记 `REBUILT_UNVERIFIED`（第 41 行），结构化子表正常回填；
  仅当 `b.rbs_id IS NULL`（简历主记录彻底不存在）才标记 `MISSING_SOURCE`。
- 生产两条软删除简历均能找到主记录，因此不会进入 `MISSING_SOURCE`，也不会被跳过。

### 3. 三条 PDF 路径缺失是否影响结构化快照？—— **PASS（不影响）**

- 结构化子表（教育/工作/项目/技能）在步骤 2（第 56 行起）从 `t_res_*` 按
  `ers_source_resume_id` 回填，**与 PDF 路径完全无关**；PDF 引用在步骤 1 统一置 `NULL`（第 40 行）。
- 步骤 5 文件迁移工作清单（第 311–319 行）以 `b.rbs_file_path IS NOT NULL` 过滤，
  这 3 条天然不进入文件复制清单，须转入《PDF 缺失记录处理与人工核查方案》。
- 注意：PDF 路径为空 ≠ 结构化简历缺失，也不等于 PDF 已彻底丢失，禁止据此排除投递或伪造文件。

### 4. 16 条 AI 分析是否全部保留？—— **PASS（全部保留）**

- 03 全程**没有任何 DELETE**，`asr_report` 原始 JSON 完整保留；DR3 仅重构主键与索引，不删数据。
- 步骤 3.1（第 169–176 行）只回填 `asr_source`、`asr_created_at`，且 `WHERE asr_source IS NULL`，
  不覆盖已绑定行。
- 步骤 4（第 245 行起）通过同一快照行关联 `app_id/snapshot_id`，不做独立 `MIN` 拼接，
  不会产生错误的跨记录关联。

### 5. manual 分析是否能够正常保留？—— **PASS（保留且可展示）**

- 步骤 3.1 对报告 JSON `$.source = 'manual'` 的行回填 `asr_source='manual'`（第 170–172 行），
  历史 1 条 manual 会被正确识别，不会被改成 llm 或 unknown。
- 后端 `ScreeningServiceImpl.saveManualAnalysis` 为独立 INSERT（追加），与 llm 共存。
- E-App 已新增独立组件 `talent_manual_score_section.dart` 展示人工分，
  并在 `talent_detail_page.dart` 第 330 行挂载；AI 组件只识别 llm 属于职责分离，不再是口径缺陷。

### 6. 是否会把重建快照错误标记为原始真实版本？—— **PASS（不会）**

- 历史重建快照统一 `REBUILT_UNVERIFIED`（第 41 行），不冒充投递时原件；
  `ers_time_source` 区分 `BACKFILL_REAL/BACKFILL_UNKNOWN`（第 43 行），
  时间无法确定时 `ers_snapshot_at` 保留 `NULL`，不用 `NOW()` 伪造。
- 原件真实性 `authenticity_verified` 默认 FALSE，须独立证据或人工确认，
  复制/归档完整性通过都不会自动升级。

### 7. 是否存在三元组非唯一更新风险？—— **PASS（DR3 已解决）**

- DR3 新增 `asr_id BIGINT AUTO_INCREMENT` 独立主键，原三元组降为普通索引，
  支持同一企业/岗位/候选人多行；新分析一律 INSERT 追加，按 `asr_created_at, asr_id` 排序取最新。
- 生产当前重复三元组为 0 组，DR3 重构无数据冲突；但仍须在执行后用
  `DR3_主键只读核对.sql` 确认主键与索引形态。

## 三、WARNING：应用层读取链路（不阻断数据库迁移）

### W1. 候选人详情页结构化简历与 PDF 仍读 C-App 当前简历

**事实（已核对源码）：**

| 入口 | 前端调用 | 后端方法 | 数据来源 |
|---|---|---|---|
| 详情页结构化简历区块 | `getTalentParsedResume` → `GET /enterprise/talent/{talId}/resume` | `TalentPoolServiceImpl.getTalentResume`（第 308 行起） | `t_res_*` 当前表 |
| 详情页“原始简历”按钮 | `getTalentResumePdf` → `GET /enterprise/talent/{talId}/resume/pdf` | `TalentPoolServiceImpl.getTalentResumePdf`（第 372 行起） | `t_res_base` 当前 PDF |
| 岗位筛选结果列表 | `GET .../tasks/.../results` | `ScreeningServiceImpl.listResults`（第 440 行起） | **企业快照** |
| AI 分析执行/人工评分 | screening 接口 | `ScreeningServiceImpl`（第 150、700 行段） | **企业快照** |

- 上述两个详情页接口以 `talId` 为入口、无 `applicationId` 上下文，后端已显式标注
  `resumeScope = current_talent_resume`（人才库当前简历，非岗位投递原件）。
- 即使从岗位上下文（带 `jobContext`）进入详情页，`talent_detail_page.dart` 第 291、237–246 行
  仍渲染这些读当前简历的区块，因此“每条投递对应自己版本”在**详情页层面尚未完全闭环**。

**影响：** 不影响本次数据迁移的安全性；但用户在 C-App 修改简历后，HR 从详情页看到的结构化内容/PDF
可能是更新后的版本，与“投递原件”预期存在偏差。

**最小修复方向（须用户批准后再做，本轮不改）：**
1. 后端新增以 `applicationId` 为入口的只读接口，复用 `EntResumeSnapshotMapper.selectByAppId`
   与 `EnterpriseResumeStorage.read` 返回该投递快照的结构化数据与 PDF；
2. 前端在岗位上下文（`jobContext != null`）下改调投递级快照接口；无岗位上下文的人才库页保留当前口径；
3. 不改动六态状态机，不重构 C-App。

### W2. 软删除后当前简历 PDF 下载会失败

- `getTalentResumePdf` 第 392 行调用 `appResumeMapper.selectResumeById`，
  该查询在 `AppResumeMapper.xml` 第 59 行带 `rbs_status = 1` 过滤；
  软删除后返回 null，第 395 行抛“简历不存在或无权访问”。
- 结构化简历（`getTalentResume`）不经过该过滤，子表数据物理保留，仍可读。
- 企业快照不受影响：快照结构化数据独立保存，PDF 若迁移成功则有独立副本。
- 这进一步说明投递级 PDF 应走快照（见 W1），当前仅作 WARNING 记录。

### W3. ScreeningMapper 遗留的当前简历查询（死代码）

- `ScreeningMapper.xml` 中 `selectCandidatesByPosition`、`selectCandidateSkills`、
  `selectEducationEvidence/selectWorkEvidence/selectProjectEvidence` 仍读 `t_res_*`，
  但主代码已无调用方（仅 `ScreeningMapperDatabaseTest` 测试引用），不影响生产链路。
- `selectResultsByPosition` 的 skills 子查询读 `t_res_skill`，
  但 `listResults` 已用快照技能覆盖缺失技能口径，仅列表行展示字段仍取当前值。
- 建议后续版本再清理，本次不重构、不删除，避免影响已验收测试。
