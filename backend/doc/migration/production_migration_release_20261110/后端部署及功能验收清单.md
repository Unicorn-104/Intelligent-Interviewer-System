# 后端部署及功能验收清单

> 适用：企业简历快照功能后端（`ruoyi-admin.jar`，版本 3.9.2）
> 原则：**用户本人手动构建、部署、重启与回滚**；本清单只提供命令、核验方法与步骤，不代替用户连接服务器。
> 部署前提：数据库正向迁移（01→02→DR3→03→04）已全部核验通过，PDF 文件迁移与人工回写策略已确定。

---

## 一、部署时机（关键顺序）

```
数据库备份 → 01 预检 → 02 建表 → DR3 主键重构 → 03 回填 → 04 核验
        → PDF 文件迁移与人工回写 → 【后端部署】→ 功能回归
```

- **禁止先部署新后端再迁移数据库**：新代码读取快照表，若表不存在会导致企业端简历/筛选接口报错。
- **也禁止长期让新库配旧后端**：旧后端不写快照，迁移窗口内的新投递不会生成快照。
- 建议在业务低峰窗口操作，数据库迁移与后端部署之间尽量缩短间隔。

## 三、JAR 核验（部署前必须做）

| 核验项 | 方法 | 预期 |
|---|---|---|
| 文件存在且大小合理 | 查看 `target/ruoyi-admin.jar` | 存在，非 0 字节 |
| 可执行 Fat JAR | `jar tf ruoyi-admin.jar | Select-String "BOOT-INF"` | 含 `BOOT-INF/classes`、`BOOT-INF/lib` |
| 主类可启动 | 见下方“启动冒烟” | 正常打印启动日志，无 Bean 装配失败 |
| 版本一致性 | 解压查看 `BOOT-INF/classes` 中配置与本次源码一致 | 与当前分支构建对应 |
| 完整性留痕 | 计算 SHA-256 并与部署记录核对 | 服务器与本机构建哈希一致 |

```powershell
# 计算 JAR 哈希（部署留痕，便于回滚核对）
Get-FileHash -Algorithm SHA256 "backend\ruoyi-admin\target\ruoyi-admin.jar"
```

### 启动冒烟（在隔离/测试环境先做）

```powershell
java -jar ruoyi-admin.jar
```
- 看到 Spring Boot 启动完成、数据源/Redis/Quartz 正常初始化，无异常堆栈即通过；
- 冒烟后停止，再到生产环境替换。

## 四、配置检查

### 1. 历史迁移开关必须保持安全默认

`HistoricalResumeMigrationConsole` 配置项（带默认值，未在 yml 显式配置时也安全）：

| 配置键 | 默认值 | 生产要求 |
|---|---|---|
| `enterprise.migration.historical-resume.enabled` | `false` | **保持 false**，避免容器启动即触发迁移 |
| `enterprise.migration.historical-resume.dry-run` | `true` | 仅在隔离环境做文件迁移时显式调整 |

- 生产正常启动**不要**打开这两个开关；历史 PDF 迁移应在隔离环境按专门流程执行。
- 该 Runner 是 `CommandLineRunner`，启动完整 Spring 容器会连库，禁止在能访问生产库的环境直接用它跑迁移。

### 2. 存储与连接配置

- 数据库连接、Redis、对象存储（S3/RustFS）地址与桶、`RuoYiConfig.profile` 路径按现有生产配置核对，
  确认企业命名空间 `enterprise-application-resume/` 所在存储可读写。
- 桶保持私有，凭据通过后端注入，不写入仓库、不随 JAR 提交明文密钥。
- 本次不修改 C-App 任何配置与打包。

## 五、部署步骤（用户手动，服务器侧）

1. 备份当前生产 JAR 与配置（保留可回退副本，不删除）。
2. 上传新 `ruoyi-admin.jar`，先放到临时目录并核对 SHA-256，确认与本机构建一致。
3. 停止现有服务（按服务器现有运维方式，`ry.sh`/系统服务等）。
4. 替换 JAR，配置文件保持不变（仅在需要时按审核结果调整）。
5. 启动服务，观察启动日志至完全就绪。
6. 执行第六节功能回归；全部通过后再恢复正常业务流量。

> 具体停启命令以服务器现有脚本和运维规范为准；本清单不提供未经用户确认的远程连接或重启操作。

## 七、失败处理与回滚

### 1. 部署后发现接口异常

- 立即保留现场日志，停止新流量；
- 用备份的旧 JAR 按同样步骤回退（旧 JAR + 原配置），重启确认服务恢复；
- 数据库侧如需回退，使用 `05_rollback.sql`（归档式：恢复原主键/索引，**保留多版本数据，不删除历史分析**）。

### 2. 回滚边界

- 数据库回滚与应用回滚是两个独立动作，按实际故障点选择，避免盲目同时操作；
- 已复制到企业命名空间的对象不自动删除，后续可凭对账流程处理；
- 不执行 `git reset/clean`、不强制推送、不删除备份；
- 所有回滚动作由用户手动执行并记录影响行数与结果。

## 八、验收结论口径

- 全部 A/B/C/D 项通过且 04 核验无异常：可判定本次后端部署 **PASS**；
- 存在非阻断展示问题（如详情页当前简历口径，见《正式迁移前阻断问题清单》W1）：记 **WARNING**，明确遗留边界后上线；
- 任一核心链路（投递快照、AI 关联、状态机）失败：**BLOCKED**，先回滚再排查；
- 尚未在目标环境执行的项目一律保持 **NOT_VERIFIED**，不得提前描述为已完成。
