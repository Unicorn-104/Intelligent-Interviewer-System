## 一、普通 private-resume 路径默认使用哪个 Bucket

**结论：裸 `private-resume/...` 不直接绑定任何 S3 桶，`readResource` 对其走本地文件系统分支。**

证据 —— `ResumePdfStorage.java`，方法 `readResource`（第 66–75 行）：

```java
public Resource readResource(Long userId, String reference)
{
    if (S3FileStorage.isReference(reference))            // 第68行：仅 s3: 开头才走对象存储
    {
        ...
        return objectStorage.read(reference, ...);       // 第72行
    }
    return new FileSystemResource(read(userId, reference)); // 第74行：裸路径走本地磁盘
}
```

- 裸路径经第 74 行 `read(userId, reference)` 解析到本地磁盘目录（`resolve`，第 129–133 行；目录由 `root()` 第 142–157 行决定，为 `ruoyi.profile` 的兄弟目录 `resume-pdf`）。
- 即裸路径是**本地存储引用**，不是 S3 key 引用；不存在“默认 S3 桶”的隐式映射。

## 二、s3: 前缀如何解析，是否允许显式指定 Bucket

**结论：`s3:` 是 S3 引用判定前缀；引用中显式携带桶名，读取按引用内桶名进行。但写入时桶名只能来自唯一配置，应用不会主动产生第二个桶。**

证据 1 —— `S3FileStorage.java`：

- 第 31 行：`isReference = reference != null && reference.startsWith("s3:");`
- 方法 `location`（第 112–122 行）：正则严格校验后，第 121 行 `return reference.substring(3).split("/", 2);` 返回 `[bucket, key]`。
- 方法 `read`（第 61–90 行）：第 63–65 行按 `location[0]`（桶）、`location[1]`（键）执行 getObject。

```java
String[] location = location(reference);
try (ResponseInputStream<GetObjectResponse> input = client().getObject(
        request -> request.bucket(location[0]).key(location[1])))   // 第64–65行
```

证据 2 —— 引用的生成只能用配置桶：`S3FileStorage.reference`（第 38–43 行）与 `store`（第 45–59 行）：

```java
String reference = "s3:" + properties.getS3().getBucket() + "/" + key; // 第40行
...
String bucket = properties.getS3().getBucket();                        // 第47行
```

- 格式上引用允许显式桶名，但该桶名在写入时恒等于 `app.storage.s3.bucket`，因此运行期实际只会出现配置的那一个桶。

## 三、是否存在多个 S3 客户端或多个 Bucket

**结论：不存在。仅 1 个 S3Client Bean、1 个桶配置。**

证据 1 —— 全仓库主代码中 S3 客户端仅一个 `@Bean`：`S3StorageConfiguration.java` 第 18–54 行（`@Bean fileStorageS3Client`），且带 `@ConditionalOnProperty(provider=s3)`。全仓搜索 `@Bean` 与 `S3Client` 无第二个生产端 Bean。

证据 2 —— 桶配置唯一：`FileStorageProperties.java` 内部类 `S3`，第 33 行 `private String bucket = "recruit-files";`，对应 `file-storage.properties` 第 5 行 `app.storage.s3.bucket=${FILE_STORAGE_S3_BUCKET:recruit-files}`。全仓搜索 `bucket` 无第二个业务桶配置（`SurveyMapper.xml` 的 `bucket` 是满意度分桶别名，与存储无关）。

## 五、普通路径在 recruit-files 下返回 404 的真正原因

**结论：裸路径是 `provider=local` 时写入的本地文件引用，文件当时落在后端本地磁盘，数据库只存相对键、无 `s3:` 前缀；这些对象没有被自动写入 `recruit-files`，故按该 key 对桶做 HeadObject 返回 404。**

证据 1 —— 上传时引用格式由 provider 决定：`ResumePdfStorage.store`（第 41–64 行）：

```java
String reference = PREFIX + userId + "/.../" + uuid + ".pdf";   // 第44–45行
if (objectStorage != null && objectStorage.enabled())           // 第46行：provider=s3 才进对象存储
{
    String stored = objectStorage.store(reference, bytes, ...); // 第48行 -> s3:bucket/key
    return new StoredPdf(stored, ...);
}
Path target = resolve(userId, reference);                       // 第51行：否则写本地磁盘
...
return new StoredPdf(reference, ...);                           // 第57行 -> 裸 private-resume/...
```

证据 2 —— 调用方原样保存该引用：`AppResumeServiceImpl.java` 第 109 行调 `pdfStorage.store(...)`，第 143 行 `resume.setFilePath(stored...reference())`。因此：

- 数据库中**裸引用 ⇔ 上传时 provider=local（本地文件）**；`s3:` 引用 ⇔ 上传时 provider=s3。
- 裸引用对象未被应用自动上传到 `recruit-files`，所以桶内查无此 key，返回 404。
- **该 404 不等同文件丢失**：文件可能仍在后端服务器本地目录（Linux 默认 `/home/ruoyi/resume-pdf/...`，即 `ruoyi.profile=/home/ruoyi/uploadPath` 的兄弟目录），或在历史人工迁移中被放到其他位置。需人工在服务器本地与对象存储分别核查。

## 六、能否通过现有 ResumePdfStorage.readResource() 直接读取

**结论：取决于运行环境与本地文件是否仍在；纯 S3 环境下不会自动从桶读取裸路径。**

证据 —— `readResource`（第 66–75 行，见问题一）：

- 裸路径恒走第 74 行本地分支，经 `read`（第 96–100 行）判断本地文件：

```java
Path path = resolve(userId, reference);
if (!Files.isRegularFile(path, LinkOption.NOFOLLOW_LINKS))
    throw new ServiceException("原始 PDF 不存在", S3FileStorage.NOT_FOUND_CODE); // 第97–98行
```

- 情形 A（provider=local 且本地磁盘文件仍在）：可正常读取。
- 情形 B（provider=s3 / 本地文件已不存在）：仍走本地分支找磁盘，文件缺失即抛 code=404；**不会**把裸路径当 S3 key 去 `recruit-files` 读取。
- 这是当前的兼容缺口：在纯对象存储环境，`readResource` 无法直接从桶里取回裸路径对应对象。

## 七、迁移程序是否会正确处理不同来源 Bucket

**结论：s3 引用处理正确；裸路径继承本地读取行为，缺失即判 SOURCE_MISSING 并转人工，不会伪造，但也不会自动映射到 recruit-files。**

证据 —— `HistoricalResumeMigrationConsole.java`，方法 `buildSourceReader`（第 114–134 行）：

```java
return (sourceResumeId, ref) -> {
    long ownerUserId = extractOwnerUserId(ref);                 // 第118行
    try (InputStream in = resumePdfStorage.readResource(ownerUserId, ref).getInputStream()) {
        return in.readAllBytes();                               // 第119–121行
    }
    catch (ServiceException error) {
        if (isNotFound(error)) return null;                     // 第126行：404 -> null（源缺失）
        throw new IllegalStateException("读取源 PDF 失败", error); // 第127行：其他错误进人工
    }
    ...
};
```

- `s3:` 引用：经 `readResource` 第 68–73 行从对象存储正确读取。
- 裸路径：经本地分支读取；本地缺失得到 404 → 第 126 行返回 null → 上游 `HistoricalResumePdfMigrator.plan`（第 163–167 行）判 `SOURCE_MISSING`，列入人工核查，**不会计算/伪造哈希**。
- 归属用户解析 `extractOwnerUserId`（第 180–186 行）：s3 引用先取 key，再 `split("/")` 取 `parts[1]`；裸路径直接取 `parts[1]`。
- 局限：程序**不会**自动把裸路径改写成 `recruit-files` 桶内对象去读取；若裸路径文件其实已被人工上传到某桶，当前程序不会自动发现。
