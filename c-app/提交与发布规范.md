# C-APP 与 Backend 提交及发布规范

本文补充本项目 `backend/` 和 `c-app/` 的协作要求，与 [仓库 Git 规范](../docs/spec/git.md) 配合执行，并由根目录 [AGENTS.md](../AGENTS.md) 作为项目 memory 引用。当前开发者姓名缩写为 **MZR**。

## 分支模型与命名

固定流转方向为 `feature/* -> dev -> main`。功能从最新 `origin/dev` 创建；若远端没有 `dev`，先从最新 `origin/main` 创建并推送 `dev`，再创建功能分支。若两个基线分支都不存在，先检查仓库初始化状态，不猜测基线。

分支格式为 `feature/<模块名>-<功能名>-<姓名缩写>`。模块和功能使用小写英文、数字与连字符，姓名缩写保留大写。简历上传解析功能使用：

```text
feature/capp-resume-upload-parse-MZR
```

每个 feature 分支承载一个完整功能。禁止直接在 `dev`、`main` 开发或推送，禁止 feature 跳过 dev，禁止强推或重写共享分支历史。

## 子功能与原子提交

每个可独立理解、验证和回滚的子功能单独 commit。本次按以下范围拆分，实际提交清单以 PR 为准：

| 子功能 | 范围 |
| --- | --- |
| 协作规范与 memory | 本文档、根目录 AGENTS.md |
| 补齐构建所需的接口源码 | 修复 data 目录误忽略，补入客户端依赖的接口封装 |
| PDF 解析与附件保存 | 逐页文本/OCR、解析配置、私有目录、鉴权读取、事务清理、迁移与相关测试 |
| AI 字段编排 | 模型配置、后端字段提示、宽松转换、自动修正及相关测试 |
| 客户端导入与自动填写 | 文件上传、草稿回填、核对保存、失败重试及相关测试 |
| 功能说明 | 原理、配置、接口、限制和部署说明 |

相关测试随对应子功能提交。不得混入独立的岗位推荐等其他功能；同一文件存在混合修改时，应拆分补丁或在独立工作区整理，并保留原工作区内容。

提交格式为 `<type>(<scope>): <中文摘要>`。允许的 type 为 `feat`、`fix`、`refactor`、`test`、`docs`、`chore`、`build`、`ci`、`perf`、`revert`；scope 使用 `capp`、`resume`、`backend`、`git` 等稳定模块名。摘要使用祈使语气、描述结果、不加句号，例如：

```text
feat(resume): 支持逐页解析 PDF 并保存私有附件
feat(resume): 按简历字段自动编排识别内容
feat(capp): 自动填入 PDF 简历并支持核对保存
```

必要时在正文写明原因、接口兼容性和验证结果。破坏性变更使用 `!` 并注明 `BREAKING CHANGE:`；关联事项使用 `Refs:` 或 `Closes:`。

## 提交前检查

先检查当前分支、远端和工作区，再检查 `git diff`、`git diff --cached` 和待提交文件清单。只暂存本子功能的明确路径，不使用全仓暂存夹带无关文件。

禁止提交密码、Token、私钥、数据库凭据、真实个人简历、上传目录、日志、构建产物及本地专用配置。配置模板仅保留环境变量占位符。根目录 `process.md` 与本机启动说明作为本地开发依据保留。

`c-app/lib/features/*/data/*.dart` 属于源码，必须纳入版本控制。运行时数据目录的忽略规则不得影响源码目录。

## 验证与 PR

每个模块完成后检查接口通断、字段对齐、数据正确性和异常分支。PR 前同步最新 `origin/dev`，解决冲突后重新验证受影响内容。

| 范围 | 必须记录的验证 |
| --- | --- |
| Backend | Maven 编译及相关测试；涉及打包和原生 OCR 时验证打包产物 |
| Flutter | 修改文件格式检查、`flutter analyze`、`flutter test`；文件上传涉及平台能力，补充 Android Debug 构建及设备验证 |
| PDF 存储 | 附件字节、元数据、归属校验、路径边界、普通编辑保留附件、替换和事务回滚 |
| AI 编排 | 使用合成数据验证字段转换、缺失值、响应异常、重试和自动填写；真实服务验证不得输出密钥及原文 |
| 数据库 | 迁移幂等、兼容性及回滚说明；已存在的共享附件字段不得直接删除 |
| 文档 | 相对链接、接口、配置与实际代码一致 |

完整功能完成后统一创建一个 `feature/* -> dev` PR。PR 写明目标、改动范围、接口或数据结构影响、验证命令与结果、人工验收情况、风险和回滚方式。未执行的检查明确标记为未验证，不以单元测试冒充完整人工验收；仍有必要验收待完成时使用 Draft PR。

默认保留原子提交并使用 Rebase merge。分支只有一个有效提交或维护者明确要求时才使用 Squash。合并必须满足人工 Review 和 CI 门禁，AI 不代替人工审核合并。

## Dev 到 Main 与回滚

`dev -> main` 仅用于完整可运行版本：计划内功能已合入、必需 CI 通过、数据库迁移可执行且有回滚路径、配置无明文凭据、后端与客户端可从干净环境构建、核心流程验收通过。功能 PR 完成不代表已满足整项目发布条件。

达到门禁后由维护者创建并审核 `dev -> main` PR。合并 main 后再创建语义化版本标签 `vMAJOR.MINOR.PATCH`。当前简历功能提交仅推进到 feature PR，发布与合并需要后续人工审核。

共享分支错误使用 `git revert` 或 Revert PR 回滚。简历功能回滚时先回滚应用代码，保留共享的附件字段和已保存 PDF，避免丢失已有数据。
