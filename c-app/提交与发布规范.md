### 接口、容器和文件迁移契约

四端继续请求共享后端；不持有 RustFS 凭据或容器内网地址。MySQL 保留业务、归属、文件名、大小和引用，
原始文件存储到 RustFS 私有桶。S3 模式写入失败须报错，不静默回退本地磁盘。
已有本地文件读取兼容用于平稳迁移，不等于已自动迁移全部服务器历史文件。

头像和通用/聊天上传保持原公开资源的访问语义，通过 `/profile/storage/` 的受限命名空间代理；
私有简历 PDF 和简历附件保留业务归属鉴权，不开放匿名直读或整个桶的公开策略。
保留原 URL、响应字段和 API 网关前缀兼容性；不得让 `/profile/storage/` 被部署层误当磁盘静态文件路径。

RustFS 为容器部署：后端是宿主机 JAR 时使用实际映射的 S3 API 端口；同 Docker 网络的后端容器使用服务名。
不得将控制台端口当 API，不为此重建现有 RustFS 容器或清空数据卷。配置详见
`backend/doc/capp_file_storage.md` 与 `deploy/backend/file-storage.example.yml`。

已有文件迁移先只读核对引用、文件存在性、归属及哈希，并保存受控的迁移前映射；
复制后下载校验，再以事务和旧值比对更新引用，提交后独立读回。超时先核对实际状态，
不得盲目重复写入或删除可能已被业务引用的对象。保留原本地文件；服务器数据迁移须走相应部署授权流程。
仓库已有的 PDF/附件表迁移必须按需核对，不重复提交本机手工执行结果、无关表结构或真实业务数据。

## Dev 到 Main 与回滚

`dev -> main` 仅用于完整可运行版本：计划内功能已合入、必需 CI 通过、数据库迁移可执行且有回滚路径、配置无明文凭据、后端与客户端可从干净环境构建、核心流程验收通过。功能 PR 完成不代表已满足整项目发布条件。

达到门禁后由维护者创建并审核 `dev -> main` PR。合并 main 后再创建语义化版本标签 `vMAJOR.MINOR.PATCH`。本次交付仅推进到 feature PR，发布与合并需要后续人工审核。

共享分支错误使用 `git revert` 或 Revert PR 回滚。简历功能回滚时先回滚应用代码，保留共享的附件字段和已保存 PDF，避免丢失已有数据。
