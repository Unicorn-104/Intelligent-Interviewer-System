## 一、项目概述

### 1.1 项目简介

企业级智能招聘面试官Agent系统是一套基于多Agent协同架构的AI原生招聘解决方案，面向中大型企业的人力资源招聘场景，覆盖从岗位发布、简历筛选、人岗匹配、AI智能面试到评估报告生成的全链路招聘流程。系统属于SaaS化智能招聘工具，支持私有化部署。

系统由四大智能Agent构成完整的“虚拟招聘团队”：AI寻聘官（自动解析JD、构建岗位画像、多平台寻访简历、人岗智能匹配、意向沟通）、AI面试官（结构化出题、动态追问引擎、多维度评分、评估报告生成）、AI面试助手（面评辅助生成、面试推荐问题）、AI应聘助手（候选人端H5页面、面试邀约与通知、面试结果查询）。

### 1.2 项目目标

**业务目标**：将初筛周期缩短60%以上，单岗位初筛时间由5个工作日压缩至2个工作日内；消除人工面试的主观偏差；释放HR约80%的简历筛选和初面工作量；支持7×24小时随时面试。

**技术目标**：AI初筛结果与终面录用结果相关性≥70%；端到端对话延迟<1秒；系统可用性≥99.9%，支持校招季50场并发面试；每次评估输出量化评分及评分理由。

## 四、技术路线

### 4.1 技术架构

系统采用分层架构设计，整体划分为六个层次：表现层、接入层、业务层、AI能力层、数据层和基础设施层。

| 层级       | 技术选型                                           | 职责说明                                   |
| ---------- | -------------------------------------------------- | ------------------------------------------ |
| 表现层     | Vue 3 + Ant Design（PC）/ Vant（H5）               | PC管理后台和H5候选人端                     |
| 接入层     | Nginx + JWT + RBAC                                 | 负载均衡、反向代理、认证鉴权               |
| 业务层     | Spring Cloud 微服务                                | 六大核心业务模块服务实现                   |
| AI能力层   | LLM网关 + RAG + Agent编排 + ASR/TTS                | 大模型调用、向量检索、工作流编排、语音服务 |
| 数据层     | MySQL + Milvus/PGVector + Redis + OSS              | 业务数据、向量存储、缓存、文件存储         |
| 基础设施层 | Docker + K8s + Prometheus + GitLab CI + SkyWalking | 容器化、编排、监控、CI/CD、链路追踪        |

### 4.3 技术选型决策依据

前端采用Vue 3而非React，主要基于团队现有技术储备和更平缓的学习曲线考虑。后端采用Spring Cloud微服务架构，主要考虑到系统未来需要支持高并发场景（校招季50场并发面试），微服务架构在水平扩展和服务隔离方面具有天然优势。AI能力层采用LangChain框架进行RAG流水线和Agent工作流编排，LLM服务选择通义千问作为主力模型（性价比高），同时预留GPT-4作为备选，支持多模型切换避免厂商锁定。向量数据库Sprint 1阶段采用PGVector以降低运维复杂度，后续根据数据规模增长可平滑迁移至Milvus。


## 五、数据库设计

### 5.1 设计规范

**规范化策略（2NF/3NF混合）**：

| 场景                     | 策略          | 理由                     |
| ------------------------ | ------------- | ------------------------ |
| 1:1传递依赖+独立生命周期 | 3NF拆表       | 需要独立查询/审核        |
| 1:1传递依赖+无独立查询   | 2NF合表       | 总是一起查询，拆表无意义 |
| 1:N关联+高频独立查询     | 3NF拆表       | 需要单独检索/排序        |
| 1:N关联+低频独立查询     | 2NF合表用JSON | 结构固定、极少单独查     |
| 聚合统计vs流水日志       | 3NF拆表       | 查询模式完全不同         |
| 大文本详情               | 2NF合表       | 详情总是随主表展示       |

**命名规范**：表名 `t_模块缩写_表名`（全小写），字段名 `表名缩写_字段名`（全小写），主键 `表名缩写_id`（bigint自增），外键 `表名缩写_关联表缩写_id`，状态字段 `_status`（tinyint），时间字段 `_at`（时间点）或 `_date`（日期），JSON字段 `_json` 后缀。

**通用字段约定**：所有业务表包含 `*_created_at`（datetime，NOT NULL，DEFAULT CURRENT_TIMESTAMP）和 `*_updated_at`（datetime，NOT NULL，ON UPDATE CURRENT_TIMESTAMP）。日志类表仅含 `*_created_at`，不允许修改。

**类型选择**：主键/外键用bigint（支持分布式ID雪花算法），状态/枚举用tinyint，金额/评分用decimal(5,2)，短文本用varchar(50~255)，长文本/评语用text，富文本/JSON用json/longtext，时间用datetime。

## 七、开发规范

### 7.1 代码规范

| 规范项   | 要求                                                         |
| -------- | ------------------------------------------------------------ |
| 命名规范 | 类名用大驼峰（PascalCase），方法/变量用小驼峰（camelCase），常量全大写下划线分隔 |
| 注释规范 | 类、方法必须包含Javadoc注释；复杂逻辑需添加行内注释；前后端接口需注明请求/响应示例 |
| 代码格式 | 统一使用IDE格式化配置，缩进4空格（Java）/2空格（前端），行宽不超过120字符 |
| 异常处理 | 禁止捕获异常后不处理；统一异常处理类；自定义业务异常需明确错误码 |
| 日志规范 | 使用SLF4J + Logback；日志包含traceId；关键操作记录INFO级别，异常记录ERROR级别 |

### 7.2 分支策略

| 分支      | 用途     | 说明                              |
| --------- | -------- | --------------------------------- |
| main      | 生产分支 | 只允许通过PR合并，每次合并打tag   |
| dev       | 开发分支 | 日常开发合并到dev，每日构建       |
| feature/* | 功能分支 | 从dev拉出，完成后合并回dev        |
| hotfix/*  | 紧急修复 | 从main拉出，修复后合并回main和dev |

### 7.3 提交规范

| 类型     | 说明      | 示例                        |
| -------- | --------- | --------------------------- |
| feat     | 新功能    | feat: 新增简历解析接口      |
| fix      | 修复Bug   | fix: 修复匹配度计算精度问题 |
| docs     | 文档更新  | docs: 更新接口设计文档      |
| style    | 代码格式  | style: 格式化代码           |
| refactor | 重构      | refactor: 重构面试状态机    |
| test     | 测试      | test: 新增匹配算法单元测试  |
| chore    | 构建/工具 | chore: 更新依赖版本         |

### 7.4 接口规范

- 所有接口遵循RESTful风格，资源名词用复数
- 统一返回格式 `{"code": 0, "message": "success", "data": {...}}`
- 分页接口统一使用 `page` 和 `size` 参数
- 时间字段统一使用ISO 8601格式
- 接口变更需更新接口文档并通知前端

### 7.5 数据库规范

- 所有表必须包含 `*_created_at` 和 `*_updated_at`
- 日志类表仅含 `*_created_at`，不允许修改
- 外键字段必须建立索引
- 禁止使用 `SELECT *`，必须明确字段
- 复杂查询需提供执行计划分析
